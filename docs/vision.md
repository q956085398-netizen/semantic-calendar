# 项目愿景

Semantic Calendar 的目标不是再做一个“能显示日期和事件”的日历，而是探索一种更自然的日历体验：

> **让日历不仅知道“什么时候发生”，也尽量知道“发生的是什么”。**

传统日历通常把所有事件都当成一段标题文字。Semantic Calendar 希望在保持轻量、隐私友好和可维护的前提下，为事件补充结构化语义，让用户能更快地从日历中理解当天真正重要的信息。

## 我们希望解决的问题

### 1. 日历信息很多，但视觉表达太弱

节假日、传统节日、比赛、会议、生日、纪念日，在传统日历里往往只是不同颜色的文本。

Semantic Calendar 希望通过统一的语义层，让这些事件能够获得更合适的图标、徽标、分类和提醒策略。

### 2. ICS 很通用，但“只负责传输，不负责理解”

ICS / WebCal 是非常成熟的日历交换方式，但大多数客户端导入后只是照原文显示。

本项目希望保留 ICS 的开放性，同时在导入后做一层本地语义增强。

### 3. 现代桌面应用不应该为了常驻而长期占用大量资源

日历天然适合全天开启，因此性能不是“以后再优化”的事情。

从项目开始就应该关注：

- 空闲内存
- 空闲 CPU
- 后台唤醒频率
- 网络请求数量
- 首次启动与恢复速度

### 4. 扩展能力不应该建立在不断堆条件判断之上

今天支持英超，明天可能是欧冠、F1、日本节假日或其他事件类型。

因此项目应该尽量形成清晰的 Provider、Matcher 和 Metadata Resolver 边界，而不是把领域规则散落在 UI 中。

## 产品愿景

理想情况下，用户导入一个普通日历源后，不需要额外整理，就能看到更有信息密度的结果。

例如：

```text
Arsenal vs Manchester City
```

不仅是文本，而是可以被理解为：

- 足球赛事
- 英超
- 阿森纳
- 曼城
- 比赛时间
- 用户关注球队
- 适合使用赛前提醒

又例如：

```text
中秋节
```

可以被理解为：

- 中国传统节日
- 农历相关事件
- 使用节日图标
- 可能适合提前一天提醒

关键不是“所有事件都必须智能识别”，而是：

> **可识别的事件获得更丰富的表达；不可识别的事件仍然作为普通日历事件正常工作。**

语义增强不能破坏日历最基础的可靠性。

---

## 产品边界

Semantic Calendar 首先是一个个人桌面日历，而不是：

- 企业协作平台
- 项目管理工具
- 在线预约系统
- 广告或内容推荐平台
- 云端账号体系优先的 SaaS
- 为了“AI”而使用 AI 的产品

我们优先解决个人使用时最常见、最稳定、最有价值的问题。

---

## 长期方向

如果基础架构足够稳定，未来可以逐步发展为：

1. 一个低资源占用的桌面日历；
2. 一个通用事件语义增强引擎；
3. 一个可扩展的日历数据 Provider 体系；
4. 一个社区可以贡献事件 Matcher 的开放项目；
5. 一个能够连接 CalDAV、Google Calendar、Outlook 等数据源，但仍保持本地优先理念的客户端。

长期目标不是追求功能数量，而是让每一个新领域都能以清晰、可维护的方式加入。
