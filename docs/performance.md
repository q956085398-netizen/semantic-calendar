# 性能基线与缓存策略（SC-020）

> 对应 [app-spec.md](app-spec.md) §15（性能需求）与 §20 发布门槛「性能基线已记录」。
> 本文件是 v0.1 的首个基线：测量方法、固定工作负载、实测数字，以及各项缓存的失效策略。

性能在 v0.1 的定位是「先建立基线，再根据实测锁定硬指标」（§15）。因此这里的数字
不是承诺，而是**同一台机器、同一份输入、同一套命令下可重复对照的起点**：改动之后再跑
一次，就能判断是变快了还是变慢了。

---

## 1. 怎么重复这份基线

### 1.1 前端与数据层（纯计算、磁盘 I/O）

```bash
npm run bench          # 等价于 apps/desktop 下的 vitest bench --run
```

- 基准文件在 `apps/desktop/src/bench/`，文件名 `*.bench.ts`，由 `vite.config.ts` 的
  `test.benchmark.include` 收集；
- 每个文件用 `// @vitest-environment node` 跑在 Node 环境：这些是纯函数与文件 I/O，
  不该被 jsdom 的开销污染；
- 单条基准的迭代次数写在各自的 `bench(..., { iterations, warmupIterations, time: 0 })`
  里——重活只跑 3 次、轻活 5–10 次，避免测量本身耗时过长；
- 报告里的 `mean` 就是本文表格采用的数字；`p99` 用来判断抖动。

### 1.2 桌面壳（窗口与进程）

```bash
npm run tauri -- build --no-bundle
powershell -ExecutionPolicy Bypass -File apps/desktop/tools/measure-desktop.ps1
```

脚本做三件事（方法与 SC-002 的人工验收一致，只是写成可重复的形式）：

1. **冷启动**：连续启动 N 次，量「进程创建 → 主窗口句柄可用」的毫秒数，报中位数；
2. **空闲资源**：窗口可见后先等 15 秒稳定（WebView 首帧、字体与懒加载都在这段时间里
   完成），再连续采两段 CPU 时间——第一段仍可能含启动尾巴，第二段才是稳态；
3. **隐藏窗口**：向主窗口发 `WM_CLOSE`（默认关闭行为是隐藏到托盘），用 `IsWindowVisible`
   确认窗口真的不可见，再采一段 CPU 时间。

> 采 CPU 用的是进程的 `TotalProcessorTime` 增量，不是任务管理器的瞬时读数——后者在
> 0% 附近的噪声比信号大。句柄必须在关闭请求**之前**取好：窗口隐藏后
> `Process.MainWindowHandle` 会指向该进程的另一个顶层窗口（WebView2 的辅助窗口），
> 拿它判断可见性会得出反结论。

### 1.3 固定工作负载

输入由 `src/bench/fixtures.ts` 生成，**全部由下标算术推导**：不使用随机数、不读时钟、
不依赖运行机器的时区。同一份生成器在任何机器上产出相同的输入，否则数字之间没有可比性。

两档规模是 app-spec §15 指定的 1,000 / 10,000 条 master（其中 5% 是带取消例外的周会，
实际入库 1,050 / 10,500 条记录）。形态分布（每 20 条一轮）：

| 形态 | 条数 / 20 | 说明 |
| --- | --- | --- |
| 普通定时事件 | 5 | Z 形态，一半带描述 |
| TZID 墙钟事件 | 3 | `Europe/London`，覆盖墙钟 → UTC 换算 |
| 全天事件 | 2 | 单日 |
| 跨天全天事件 | 1 | 1–3 天 |
| 每周重复 | 2 | 一半 `COUNT=40`，一半 `UNTIL=…Z`；覆盖两条边界分支，两条都带 VALARM |
| 每月重复 | 1 | `FREQ=MONTHLY;COUNT=24` |
| 隔日重复 + EXDATE | 1 | 覆盖排除分支 |
| 英超比赛 | 3 | 对阵从真实目录的赛季名单成对取队，保证 Matcher 真的命中 |
| 带 VALARM 的独立事件 | 2 | 覆盖提醒链路（连同上面两条周会，共 4/20 带提醒） |

比赛对阵刻意不写死队名：从 `footballCatalog` 的赛季名单里成对取，名单变化时夹具自动
跟随，不会悄悄退化成「一条都匹配不上」的空转。

- **WebCal 304 与 200 的差距**（10,000 条：< 0.05 ms vs 86.6 ms）就是条件 GET 省下的

- **导入总时长 320 ms** 包含四个阶段，其中只有「解析 + 落库」（83 ms）与「读模型」
  （37 ms）是不中断的同步段，增强已分片（见 §3.2）。这是一次用户主动触发的动作，
  不是常驻开销。

## 3. 这次基线带来的改动

### 3.1 月切换：597 ms → 152 ms（10,000 条）

优化前的实测链条（同一台机器；每步之后重跑）：

| 版本 | 10,000 条 | 1,000 条 |
| --- | --- | --- |
| 优化前（当时夹具只有 `COUNT` 周规则） | 597 ms | 51 ms |
| + 窗口前候选不物化 + 格式化器缓存（夹具改为 `COUNT` / `UNTIL` 混合，口径更严） | 310 ms | 33 ms |
| + `UNTIL` 边界快路径 + 单次事件窗口预筛（最终） | 152 ms | 16 ms |

三处改动都在 `src/normalize/occurrences.ts` 与 `src/format/time.ts`，语义不变：

1. **窗口之前的候选只计数、不物化**。展开器从 DTSTART 起生成候选，原先对每条候选都做
   时区换算与 EXDATE / 例外匹配，哪怕它远在窗口之前——一条从 1 月开始的每周事件在 11 月
   的窗口里，九成候选都是这种。现在这些候选照常参与 `COUNT` 计数与 `UNTIL` 判断，
   只是不物化（日期级比较，留一天余量）。
2. **`UNTIL` 边界快路径**。候选日 + 1 天仍早于 `UNTIL` 的日期时，任何时区下都早于边界
   （偏移最大 ±14 h，跨不过一整天），无需逐候选做换算。
3. **`Intl.DateTimeFormat` 按用途缓存**（`src/format/time.ts`）。构造一个格式化器约 50 µs，
   比它自己的 `format` 贵两个数量级，而它在分桶、月格摘要、Inspector、提醒文案里都是
   逐条事件调用的。原先有 6 处调用点各自 `new`（`normalize/timezone.ts` 早已自带一份
   按 tzid 的缓存，不在其中），现在每个用途在 `format/time.ts` 里各缓存一份实例，
   顺带把「Z 形态换算 / 墙钟形态切片」这条共同规则收进 `localTimeOfDayLabel`。

### 3.2 语义增强分片（`src/semantic/enrich.ts`）

`reEnrichStoreYielding` 把「清空增强分区 → 逐条匹配 → 写回」拆成每 500 条一片的任务，
片间用 `scheduling/yield-to-main.ts` 让出主线程（MessageChannel 任务，不是 `setTimeout`
——Chromium 对隐藏页面会把定时器节流到每秒甚至每分钟一次，那会把一次后台刷新拖成几十秒）。
同步入口 `reEnrichStore` 与它共用同一份生成器实现，结果逐字节相同。

启动重建、订阅刷新、导入这三条「事件量由用户数据决定」的路径都走分片入口：单片约 3 ms，
界面在处理期间保持可绘制。

分片让出主线程之后，两次重建就可能重叠（一次导入与一次后台刷新同时发生），而重建是
「先整体清空再重建」——重叠会让后一次在前一次的中途清空分区，最终分区里混着两个快照的
产物，旧快照里已被删除的事件留下永远不再显示的孤儿记录。因此**同一次存储上的重建排队
执行**（`rebuildQueueByStore`）：每次重建都以自己开始时的最新事件集为准，最后一次完成的
结果是权威的。`enrich.test.ts` 里有一条专门的用例——在第一次重建让出主线程时删掉事件并
立刻发起第二次重建——去掉队列它会失败。

### 3.3 月切换读取分片（`src/calendar/month-occurrences.ts`）

§3.1 把展开本身从 597 ms 降到 152 ms，但那仍是一次**同步**计算：它挂在渲染路径的
`useMemo` 里，不让出主线程——10,000 条事件下切换月份就是一次约 160 ms 的卡顿，对
§15 的「月视图切换应感知即时」偏高。这次把读取路径也拆成短任务：

- **展开仍是同一份实现**：`normalize/occurrences.ts` 的同步入口就是分片生成器的一次
  排空，两条路径不可能各自演化出不同的语义；
- **按时间阈值让出**：`calendar/month-occurrences.ts` 让一个任务连续算到超过
  `MONTH_YIELD_AFTER_MS`（5 ms）为止，任务之间用 `scheduling/yield-to-main.ts` 让出
  （与 §3.2 的增强分片同一机制）。阈值是**软**的：时间检查在每片之后，因此一次任务
  还会多跑一片（128 条事件），末次任务还要多做一次分桶；
- **常见规模在第一个任务里算完**：第一个任务在渲染期跑，与这次渲染同一帧，因此小日历
  切换月份不会出现「先空一下再填上」；只有大数据量才进入整理状态；
- **整理期间不发布半份结果**：月格为空 + 表头状态行说明工作量
  （`monthOccurrencePendingText`），算完一次性给出完整月格——半份结果会让月格与详情栏
  在几帧内反复变化，比一次短暂空白更难解释。

`npm run bench`（2026-09-25 追加；表里每行都是同一份基线里的实测 `mean`）：

| 段 | 1,000 条 | 10,000 条 |
| --- | --- | --- |
| 改动前：一次同步任务（§2.1 的展开 + 分桶） | 17.4 + 0.7 ms | 163.7 + 7.6 ms |
| 改动后：单次任务（主线程上最长的一段） | 6.3 ms | 6.6 ms |
| 让出一次（`src/bench/scheduling.bench.ts`） | 0.0033 ms | 0.0033 ms |
| 第一个任务能算完的规模上限（实测 200 条 3/3 次算完，300 条 0/3 次） | 约 200 条 | — |

读法：

- **单次任务**是这次改动的核心数字：10,000 条从一次 171 ms（展开 + 分桶）降到 6.6 ms
  （5 次采样抖动 ±0.8%），主线程上不再有可感知的卡顿；最坏的一次是末次任务——它多做了
  一次分桶（10,000 条 occurrence 7.6 ms，分桶本身没有时间检查），约 14 ms，仍在一帧内；
- **让出本身可以忽略**：一次约 3 µs（连续 20 次共约 25 µs），因此整段墙钟时间与同步
  路径同量级。整段总时长刻意不写进这张表：同步 / 分片两条对照行的差值在两次运行间是
  +2.5% 与 −39%，测量抖动（±40%）比被测差异大，**引用它只会得出错误结论**；
- **约 200 条以上的日历会进入整理状态**：1,000 条（约 34 ms 工作量）拆成约 5 次任务，
  状态行出现约 2–3 帧，然后月格补齐。这是分片的代价，也是它与「卡 34 ms」之间的取舍；
  200 条以下的日历与改动前完全一致（首帧即完整月格，没有状态行）；
- §2.1 的「展开重复规则 151.91 ms」与本次重跑的 163.7 ms 是同一段代码的两次测量
  （相差 8%，堆状态不同），说明这份基线的行间比较本来就有抖动——相邻测量的行才可比。

## 4. 缓存与失效策略

v0.1 的缓存不多，但每一条都有明确的失效规则；没有「顺手加一层、什么时候清掉没人知道」
的缓存。

| 缓存 | 内容 | 失效 / 更新规则 | 覆盖它的测试 |
| --- | --- | --- | --- |
| WebCal 校验值 | `ETag` / `Last-Modified` | 每次 200 **整体替换**：服务端不再返回时旧值被清掉（否则会一直用过期校验值发条件请求）；304 只推进 `lastCheckedAt` | `data/webcal/webcal-refresh.test.ts`：「200 且服务端不再返回校验值时清掉旧值」「第二次刷新带上校验值，304 时事件不变但状态推进」 |
| WebCal 事件集（订阅缓存） | 该来源的全部事件 | 200 按 `(sourceId, uid, occurrenceId)` 键差集替换：批次中消失的删除，仍在的保留（增强结果不因刷新被丢弃）；失败 / 超时 / 空响应**一律不动**旧事件，只标记状态 | 同上：「全量替换：源里消失的事件被删除」「网络异常保留旧事件与上次成功时间」「空日历不清空已有缓存」 |
| 语义增强结果 | Matcher / Resolver 产物 | 事件内容更新时按事件失效（`upsertEvents` 删除该键的增强）；重建时整体清空重算；来源删除时级联删除 | `semantic/enrich.test.ts`（重建清除过期增强）、`data/store/calendar-store.test.ts` |
| 事件集合版本号（本次新增） | `CalendarStore.eventsRevision()`：可见事件集合的单调计数 | 只在集合真的会变时推进（事件增删改、来源启停、来源删除）；来源状态 / 校验值这类不动事件的改动不推进。App 据此跳过重读事件——304 与失败刷新因此不再白克隆一遍事件、也不再让月格闪一次「整理中」 | `data/store/calendar-store.test.ts`「可见事件集合的版本号（SC-020）」一组；`App.test.tsx`「304 刷新不重算月格」 |
| 已处理提醒日志 | `notifications.firedReminders` | 保留 30 天、最多 500 条，超出即裁剪——它是去重状态而不是历史记录，无界增长会让每次落盘变大 | `notifications/fired-reminders.test.ts` |
| 本地 ICS 导入 | 事件（增量 upsert） | 同 `(sourceId, uid, occurrenceId)` 命中即更新，不删除文件中已消失的事件；全量替换语义只属于 WebCal 刷新 | `data/import/import-local-ics.test.ts` |
| `Intl` 格式化器（本次新增） | 常量选项的 `DateTimeFormat` 实例 | **不失效**：选项是常量，实例只依赖进程启动时的默认语言与时区。运行期改系统时区 / 语言需重启生效（与 v0.1 其余「启动时确定」的行为一致） | `format/time.test.ts` |

没有缓存的（也不需要）：

- **队徽 / 联赛 Logo**：仓库不分发任何图片（开发原则 §10），`semantic/marks.ts` 的解析是
  无状态的；资源包接入后命中的是 WebView 自己的图片缓存（同 URL 不重复下载），应用不再
  叠一层——否则就有了第二个需要失效策略的缓存。
- **中国日历数据**（农历 / 节假日 / 节气）：内置数据表，没有网络来源，按年份登记并带
  `version`（CN-007），改动走代码评审而不是缓存失效。
- **本地快照**：它是数据的权威副本，不是缓存。

## 5. 后台唤醒（app-spec §12）

约束是「避免高频轮询」，实现上只有一次性定时器：

- **WebCal 刷新调度器**（`data/webcal/refresh-scheduler.ts`）：只维护一个 `setTimeout`，
  指向最近一个到期时刻，触发后重算；没有到期订阅时**完全不持有定时器**（空闲零唤醒）；
- **提醒调度器**（`notifications/notification-scheduler.ts`）：同样只有一个 `setTimeout`，
  指向「下一条提醒」与「下一个本地零点」中更早的一个；
- **桌面壳**：Rust 侧没有定时器、没有睡眠循环，隐藏窗口只是停止渲染。

`scheduling/no-polling.test.ts` 把这条约束变成可执行断言：扫描 `src/`（除测试外）不允许
出现 `setInterval`，扫描 `src-tauri/src/` 不允许出现周期定时器或睡眠循环。调度器本身的
行为（空闲零唤醒、只持一个定时器、`stop` 后不再安排）由各自的单测覆盖。

## 6. 已知边界

- **月切换读取已分片**（2026-09-25 追加，见 §3.3）：单次任务 6.3–6.6 ms（10,000 条），
  最坏一次约 14 ms（末次任务多一次分桶），让出约 3 µs。代价有两条，都如实记在这里：
  约 200 条以上的日历会拆成多次任务，表头整理状态行出现约 2–3 帧；整理期间月格是空的
  （不给半份结果），文案说明工作量。约 200 条以下仍在第一个任务里算完，界面与改动前一致。
- **导入的解析与落库段不拆分**（10,000 条约 83 ms）：解析是单趟文本处理，要让它不占主
  线程需要把整条管线搬进 Web Worker，那是架构变化而不是优化；增强段与读取段已分片，
  剩余的不中断时长如实记录在这里。
- **月切换里剩下的同步段都在一帧预算内**：建网格 0.010 ms、按日期分桶 7.6 ms、
  日级语义载荷 1.5 ms、标记解析 0.0013 ms（10,000 条口径）——不再拆分，否则只是把
  开销挪来挪去。
- **提醒计划的重建仍是同步段**：`planReminders` 的输入是「当前日期起 30 天」窗口里展开
  好的 occurrence，展开（10,000 条约 154 ms）与计划（约 4.6 ms）都在调用方那一次调用里
  完成（`createNotificationScheduler` 的 `plan` 回调），因此每次数据变化都会有约 159 ms
  不中断。它不在渲染路径上，只在启动、数据变化、跨天与到点这四种时刻发生一次；本次没有
  一起分片（切片方案与数字记在 `src/bench/reminder.bench.ts`），已另开 Ticket 跟踪。
- **304 / 失败的刷新不再触发重算**（SC-020 的缓存失效）：读取事件是逐条克隆
  （10,000 条约 37 ms），而 304 刷新只改来源状态与校验值。存储现在用
  `eventsRevision()` 报告「事件集合是否真的变过」（事件增删改、来源启停、来源删除才推进），
  App 据此跳过重读——否则每次后台刷新都会白读一遍、让月格闪一次「整理中」。
- **性能目标尚未锁定硬指标**（§15：先建立基线，再根据实测锁定）：本文件是基线，不是
  门槛；发布前若需要硬指标，应从这里取数并写回 app-spec。
- **图片缓存不在应用内**：应用只负责把逻辑引用解析成地址并在缺失时降级，缓存由 WebView
  负责。
