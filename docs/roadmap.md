# 开发路线草案

这是一份方向性 Roadmap，不代表固定发布日期，也不作为 Issue 列表使用。

## 阶段 0：验证技术栈

目标：确认 Tauri + React + Rust 是否满足轻量常驻需求。

需要验证：

- Windows 构建流程
- 基础月视图
- 窗口隐藏 / 恢复
- 系统托盘
- 本地通知
- 空闲内存和 CPU
- 打包体积

如果技术栈在真实测试中不合适，应允许调整。

---

## 阶段 1：日历基础

目标：成为一个可用的本地日历。

建议范围：

- 月视图
- 日期导航
- 基础事件详情
- 本地 ICS 导入
- 统一事件模型
- 基础本地存储
- 明暗主题

完成这一阶段后，即使完全没有语义增强，也应该已经是一个能正常使用的简单日历。

---

## 阶段 2：ICS / WebCal

目标：建立稳定的数据输入层。

建议范围：

- ICS 文件导入
- ICS URL 订阅
- 刷新
- UID 去重
- 重复事件
- 全天事件
- 时区
- 错误提示

这部分是后续所有功能的基础，应优先保证可靠性。

---

## 阶段 3：事件语义框架

目标：完成 Normalizer、Matcher Engine 和 Metadata Resolver。

第一阶段不需要支持很多 Matcher，只要框架真实可用。

建议先实现：

- 通用 Normalizer
- Matcher 注册
- 优先级
- MatchResult
- 元数据解析
- 未识别事件回退机制

---

## 阶段 4：中国日历

目标：补充本地化价值。

建议加入：

- 法定节假日
- 调休 / 补班
- 传统节日
- 二十四节气
- 农历显示

这里需要特别注意数据准确性和年份更新机制。

---

## 阶段 5：英超

目标：验证“语义日历”的核心特色。

建议范围：

- 英超赛事识别
- 20 支球队识别
- 主客队识别
- 用户关注球队
- 球队元数据
- 徽标显示
- 赛前提醒
- 常见标题格式兼容

如果这一阶段体验成立，项目的核心价值基本被验证。

---

## 阶段 6：性能与稳定性

目标：让应用适合真正长期常驻。

重点：

- 启动速度
- 空闲内存
- 空闲 CPU
- 大日历导入
- Matcher 批处理
- 后台刷新
- 通知可靠性
- 崩溃恢复

---

## 阶段 7：更多数据源

在核心稳定之后再考虑：

- CalDAV
- Google Calendar
- Outlook / Microsoft 365
- 更多国家节假日
- 更多体育赛事

不要在核心模型稳定前同时接入大量外部平台。

---

## 判断是否进入下一阶段

每一阶段都应满足两个条件：

1. 当前能力可以独立使用；
2. 没有已知的结构性问题需要先解决。

Roadmap 的作用是控制范围，而不是制造进度压力。
