## Spec

### R1 · P1：并发 304 刷新可使新比赛长期停留在普通事件显示

对应规格：“读取结果发布保持一致”“日级语义与事件都对应当前选择”，以及比赛语义展示与可配置提醒的成功标准。

位置：

- `App.tsx:608–610` 仅按原始事件的版本跳过 UI 重读。
- `calendar-store.ts:531` 原子提交增强分区，但不推进该读取版本。

复现过程（真实 App 集成，桌面 IPC 为既有测试替身）：

1. 启动两个已启用的 WebCal 来源 A、B，均有最近刷新时间，避免自动后台刷新干扰。
2. A 手动刷新返回 200，真实解析并提交一条 `Arsenal vs Manchester City`，在语义增强开始时暂停其异步完成，模拟分片让出。
3. B 手动刷新返回 304，完成落盘和 UI 读取。此时原始事件版本已推进，但 A 的完整增强结果尚未提交，因此 UI 读到普通比赛标题并记下该版本。
4. 放行 A，使用实际 Matcher、Resolver 和增强重建，等待最终落盘。
5. 确认最终快照中的增强记录含完整 `metadata.fixture`，再要求真实月格出现 `.match-cell`。

结果：快照的比赛元数据断言通过，但月格比赛块断言失败（null）；界面仍显示普通标题。相同场景重复检查结果一致。A 完成后的重读被同一原始事件版本挡住，因此不会自动恢复，需另一事件变更或重启才可能重读。比赛提醒计划也消费这份 UI 事件集合，可能随之遗漏；本次直接动态证明的是月格语义缺失。

建议修复：让增强结果成功提交参与读模型失效机制，例如独立的读模型/增强版本；读取完整版本并正确处理并发重建。保留“真正没有数据变化的 304 不白重算”优化，不能简单地靠每次 304 都全量重读。加入本场景的 App 集成回归，并覆盖另一来源失败刷新的相同路径。

复现片段保存在 `.scratch/sc025-concurrent-review-repro.txt`，可附加到现有 App 集成测试后运行；其复用现有 helper，并在暂停后仍调用实际增强实现。临时完整测试副本已删除，未留下一套故意失败的测试。
