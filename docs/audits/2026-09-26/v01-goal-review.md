## 已复现的缺陷

### R1 · P1：切换月份后，保留的选中日期丢失详情

- 对应目标：CAL-003、V0.1 成功标准第 2/5/7 项；SC-005，连带中国日历与赛事详情。
- 复现：固定日期为 2026-09-23，启动后右栏有该日农历；点击主月历“下一月”。右栏日期仍为“9月23日”，农历内容变为 undefined。同一查询方式也让网格外日期的事件、假期与节气消失。
- 原因：`App.tsx:384–409` 的事件和日级语义只为当前月网格构造；`stepMonth()`（1051）不更新选择；Inspector（1261–1265）继续拿旧选择查询新网格。
- 验证：临时集成用例在切月前确认农历存在，切月后确认日期未变，再要求农历保留；最后一项失败。
- 建议验收：选中有比赛/假期的日期后连续切月，右栏日期与完整详情保持一致；可为选择日期单独查询，不必依赖可见网格。

这也是早前运行审查 R2；`fixes.md` 明确仍待处理，本次重新确认。

### R2 · P1：长期常驻跨午夜后，“今天”停留在启动日期

- 对应目标：成功标准第 1/2 项、CAL-001 今天状态、CAL-002 回到今天。
- 复现：2026-09-23 启动，时钟推进至 09-24，再点击“今天”；实际 today 标记仍是 `2026-09-23`，不是 `2026-09-24`。
- 原因：`App.tsx:267` 用只有读取方的 `useState(() => new Date())` 固定 today；`todayKey`、网格和 `goToToday()`（1056）始终使用该日期。提醒的跨天重算没有更新这个 UI 状态。
- 验证：临时集成用例用假时钟推进日期并点击真实按钮，断言失败，实际值为旧日期。
- 建议验收：跨普通日、月末和年末后，今天标记和“回到今天”都跟随当前本机日期；从托盘恢复也应校正。复用跨天/恢复触发，避免增加高频轮询。

### R3 · P1：删除正在解析的订阅后，刷新写回无来源事件

- 对应目标：SC-007“可删除订阅”、设置的来源删除级联规则、持久化可靠性。
- 复现：订阅返回 260 条事件；网络请求已完成、解析分片第一次让出主线程时删除来源；随后让刷新继续完成。来源不存在，但该来源的事件数为 260，预期为 0。
- 原因：`data/webcal/webcal-refresh.ts:199` 仅在收到 HTTP 响应后检查来源是否存在；224/260/264 行之后还有异步分片，删除可以在这些让出点发生，后续落库没有再次检查。刷新和删除操作均可在 App 中独立触发。
- 验证：临时用例通过现有 `yieldToMain` 注入点模拟解析期间的删除，使用真实解析、标准化及 CalendarStore；最终 `listEvents(sourceId)` 长度断言失败（260）。不需要真实网络，也没有写入用户日历。
- 影响：删除后重新留下无来源记录，之后 App 的刷新结果落盘可把它们保存；同一地址重新添加时也有重新读到残留记录的风险。
- 建议验收：分别在下载、解析、标准化和落库阶段删除订阅，最终来源、原始事件和增强结果均为空；用操作代次/取消判据与可控提交边界保证删除不被晚到刷新覆盖。
