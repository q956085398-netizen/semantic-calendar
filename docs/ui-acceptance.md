## 1. 怎么读这份记录

每条验收项给三样东西：

- **判据**：这条验收在问什么（把 §26 的一句口号还原成可检查的事实）；
- **自动**：可执行的回归证据（测试文件与用例名）。改坏了会红，不依赖人记性；
- **人工**：必须在真实渲染里看的部分，附截图文件名（见 §6）。

「自动」一栏不是装饰：§26 里超过四分之三的条目在 jsdom 与 CSS 契约层面就能判定
（裁切、优先级、只渲染一次、层级可读），只有布局、观感与整屏构图必须用眼睛看。
两类证据都有的条目，以人工记录为准——测试能证明结构，证明不了「看起来对不对」。

## 5. 本次发现的问题

两条：一条（5.1）由 SC-023 修复后复检通过，一条（5.2）只能算部分通过，等 SC-022 的资源包。

### 5.1 默认窗口尺寸下比赛格裁掉第二个队标（SC-023 已修复，复检通过）

**现象**：1180×760（应用默认窗口）且左右栏展开时，比赛格里的「队标 VS 队标」放不下，
第二个队标被格子的裁切边界切掉一截（能看到 `MC` 与半个 `E`），读不出是哪支球队。

**量化**：对阵块可用宽度 62px（格子 82px 减去内边距），内容需要 81px（两个 26px 队标
+ `gap: 6px` ×2 + 「VS」）。缩到 820×560（两侧 rail 折叠、格子回到 111px）时完整显示。

**为什么测试没拦住**：jsdom 没有布局，`calendar/MonthView.test.tsx` 只能断言「格子里
只有队标与 VS」；`cell-visual-contract.test.ts` 断言的是格子必须裁切（§10.1 对狮标的要求），
而裁切恰好是这里把队标切掉的原因。这条只有真实渲染能看出来。

**性质**：不是本次改动引入的回归——既有实现（SC-016）在默认窗口尺寸下就是这个样子。
裁切本身按 §10.1 是对的（狮标必须裁在格内），问题是对阵块没有随格子宽度收缩。

**影响范围**：对阵块需要 81px 内容 + 20px 格内边距（`padding: 8px 10px`）= 101px 的格子，
即月历区约 753px、窗口约 1310px 以上才放得下。因此窗口窄于约 1310px 且左右栏展开时
都会出现——包括应用自己的默认尺寸 1180×760 与 1280 宽的窗口（1366 宽时格子约 108px，
刚好够放下）。

**修复（SC-023）**：改成随格子宽度收缩，形态与口径都不动（§10.2 仍是「队标 VS 队标」，
§10.1 的狮标裁切不动，§22 仍是布局决定 Logo 如何被显示）：

- `.month-cell` 成为尺寸查询容器（`container-type: inline-size`，只做 inline-size 包含，
  格子宽度仍由网格轨道决定）；
- 队标 / 间距 / VS 字号改成以 `cqi`（格子内容盒的百分之一）为基准的 `clamp()`，
  上限是原来的固定值（26px / 6px / 10px，宽窗口回到原设计），下限是「3 字母 fallback
  仍可读」（16px / 2px / 8px）；队标自己的字号与圆角同样跟着缩（否则 16px 的队标
  留着 26px 时的 10px 字号与 8px 圆角会糊成一个读不出队名的圆点）；
- 对阵块自己的水平内边距 4px → 2px，把宽度让给队标。

各档尺寸下的实测（Chromium，真实 `index.css` + 真实 `MonthView`）：

| 场景 | 月历区 | 格子 | 队标 | 对阵块 | 到裁切边界的余量 |
| --- | --- | --- | --- | --- | --- |
| 1081 窗口（双栏展开的最窄情况） | 521px | 67.6px | 16px | 47.5px | 8.1px（居中退化为左端排起，偏移 3.9px） |
| 1180×760 默认窗口 | 620px | 81.7px | 18.5px | 53.9px | 13.9px |
| 1280 窗口 | 720px | 96.0px | 22.8px | 66.4px | 14.8px |
| 820×560 最小窗口 | 780px | 104.6px | 25.4px | 72.6px | 16.0px |
| 1366 宽窗口 | 806px | 108.3px | 26px | 74.2px | 17.0px |
| 1680 宽窗口 | 1120px | 153.2px | 26px | 77.4px | 37.9px |

**已知下限**：下限那一档（格子窄于约 73px，即窗口 1081–1134px）队标 16px、fallback 文字
6.5px——这是「不裁切」与「字号够大」之间的取舍点，这里选的是不裁切。信息本身不丢：
hover 与读屏始终给出完整对阵与开赛时间（§18.1）。

**复检方式**：默认窗口的月历区宽度（620px）取自真实三栏布局（`232 / 620 / 288`，与改动前
逐像素一致），比赛视觉需要本地数据层、浏览器预览没有，因此复检在 Chromium 里直接渲染
真实 `MonthView` 组件 + 真实 `index.css`，事件由真实链路产出（同一份 §2 的 ICS 经
ICS → Normalize → Matcher → Resolver），月历区宽度按场景取 521 / 620 / 780 / 806 / 1120px。
**这套测量台是临时的、没有进仓库**（只有一个 HTML 入口加一个把 `MonthView` 挂起来的
tsx），因此截图只能复看、不能一键重跑；可执行的回归证据是下面那条契约测试。

同一套装置把改动前的固定尺寸装回去，复现出「对阵块 77.4px 放进 57.7px、第二个队标被
切 9.7px」（截图 09），与现象一致，因此前后可比。

**两档「本来就正常」的尺寸**：820×560 与更宽窗口的可见性不变，但队标比原来略小
（820×560 下 25.4px、1366 下 26px），要到约 1366 宽才完全回到原设计尺寸。这是同一条
等比规则的结果——没有为这两档单独开一条分支，代价是它们也按格子宽度缩放了一点点。

**自动回归**：`calendar/match-cell-fit-contract.test.ts` 把这条从「靠眼睛」变成可执行断言——
从 `index.css` 读出声明的系数，按真实的窗口 → 月历区 → 格子宽度算一遍对阵块需要多宽，
断言 §26 第 12 项要求的三档尺寸下都放得下且留有余量、最窄的格子（左右栏都展开的最小
窗口）不越出裁切边界、宽格子仍回到原设计尺寸。窗口宽度、三栏 token、列数与列间距、
折叠阈值都从 `tauri.conf.json` / `index.css` / `AppShell.tsx` 读，不另抄一份——调参后
不会留下「界面变了、断言还是绿的」这种假通过。把固定尺寸或过大的系数改回去，它会红。

**截图**：06（默认窗口浅色，09-26 与 10-04）、07（最小窗口）、08（默认窗口深色）、
09（同一装置下改动前的样子）、10（最窄比赛格：1081 窗口，居中退化为左端排起）。

### 5.2 节日 / 节气的照片背景本次看不到（部分通过，等 SC-022）

§26 第 10 项与参考示例图里，中秋、寒露、霜降这类日子有照片型背景（月亮、结霜的草）。
本次验收看到的只有语义文字与节气标签——仓库不分发图片资源（开发原则的版权边界，
SC-014 / SC-016 都记着这件事），`display/DayBackdrop.tsx` 在没有资源时按「不画背景」
降级，这正是 `DayBackdrop.test.tsx` 覆盖的行为。因此这一条的能力成立、画面未达参考图，
差异的来源不是本次的实现而是资源接入，判为部分通过；资源包接入与许可审查在 SC-022，
那一单完成后需要按本文 §6A 再看一眼 2026 年 10 月（寒露 10-08）与 9 月（中秋节 09-25）。

## 6. 复现方式

### A. 不需要数据（主题、假期、节气、折叠、最小窗口）

```bash
cd apps/desktop
npm run dev
```

浏览器打开 `http://localhost:1420/`，用主导航切到 2026 年 10 月（国庆连休与补班）、
点侧栏「设置」→「外观」切深色、点左右栏底部的「收起」、把窗口缩到 820×560。

cd apps/desktop
