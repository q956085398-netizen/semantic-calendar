## 1. 怎么读这份记录

每条验收项给三样东西：

- **判据**：这条验收在问什么（把 §26 的一句口号还原成可检查的事实）；
- **自动**：可执行的回归证据（测试文件与用例名）。改坏了会红，不依赖人记性；
- **人工**：必须在真实渲染里看的部分，附截图文件名（见 §6）。

「自动」一栏不是装饰：§26 里超过四分之三的条目在 jsdom 与 CSS 契约层面就能判定
（裁切、优先级、只渲染一次、层级可读），只有布局、观感与整屏构图必须用眼睛看。
两类证据都有的条目，以人工记录为准——测试能证明结构，证明不了「看起来对不对」。

## 5. 本次发现的问题

两条：一条（5.1）由 SC-023 修复后复检通过，一条（5.2）只能算部分通过，SC-022 已就该条定下 v0.1 口径（不接入照片资源，见 §5.2）。

### 5.1 默认窗口尺寸下比赛格裁掉第二个队标（SC-023 已修复，复检通过）

**现象**：1180×760（应用默认窗口）且左右栏展开时，比赛格里的「队标 VS 队标」放不下，
第二个队标被格子的裁切边界切掉一截（能看到 `MC` 与半个 `E`），读不出是哪支球队。

**量化**：对阵块可用宽度 62px（格子 82px 减去内边距），内容需要 81px（两个 26px 队标

- `gap: 6px` ×2 + 「VS」）。缩到 820×560（两侧 rail 折叠、格子回到 111px）时完整显示。

**为什么测试没拦住**：jsdom 没有布局，`calendar/MonthView.test.tsx` 只能断言「格子里
只有队标与 VS」；`cell-visual-contract.test.ts` 断言的是格子必须裁切（§10.1 对狮标的要求），
而裁切恰好是这里把队标切掉的原因。这条只有真实渲染能看出来。

**性质**：不是本次改动引入的回归——既有实现（SC-016）在默认窗口尺寸下就是这个样子。
裁切本身按 §10.1 是对的（狮标必须裁在格内），问题是对阵块没有随格子宽度收缩。

**影响范围**：对阵块需要 81px 内容 + 20px 格内边距（`padding: 8px 10px`）= 101px 的格子，
即月历区约 753px、窗口约 1310px 以上才放得下。因此窗口窄于约 1310px 且左右栏展开时
都会出现——包括应用自己的默认尺寸 1180×760 与 1280 宽的窗口（1366 宽时格子约 108px，
刚好够放下）。

**修复（SC-023）**：改成随格子宽度收缩，形态与口径都不动（§10.2 仍是「队标 VS 队标」，
§10.1 的狮标裁切不动，§22 仍是布局决定 Logo 如何被显示）：

- `.month-cell` 成为尺寸查询容器（`container-type: inline-size`，只做 inline-size 包含，
  格子宽度仍由网格轨道决定）；
- 队标 / 间距 / VS 字号改成以 `cqi`（格子内容盒的百分之一）为基准的 `clamp()`，
  上限是原来的固定值（26px / 6px / 10px，宽窗口回到原设计），下限是「3 字母 fallback
  仍可读」（16px / 2px / 8px）；队标自己的字号与圆角同样跟着缩（否则 16px 的队标
  留着 26px 时的 10px 字号与 8px 圆角会糊成一个读不出队名的圆点）；
- 对阵块自己的水平内边距 4px → 2px，把宽度让给队标。

各档尺寸下的实测（Chromium，真实 `index.css` + 真实 `MonthView`）：

| ------------------------------- | ------ | ------- | ------ | ------ | --------------------------------------- |

**已知下限**：下限那一档（格子窄于约 73px，即窗口 1081–1134px）队标 16px、fallback 文字
6.5px——这是「不裁切」与「字号够大」之间的取舍点，这里选的是不裁切。信息本身不丢：
hover 与读屏始终给出完整对阵与开赛时间（§18.1）。

**复检方式**：默认窗口的月历区宽度（620px）取自真实三栏布局（`232 / 620 / 288`，与改动前

> - **越界是有意的**——「不完整」的字与放大的 Logo 靠负偏移越出格边、再由裁切收住；
>   把偏移改回正值，字就完整了、也不再被裁（同上文件的「大字与狮标是有意越界的」，
>   狮标那一半对应的正是 §26 第 11 项记录里「按 right/bottom 负偏移铺出格边界后被裁」的形态）；
> - **§20 的分色口径**——休假 / 补班 / 节气 / 比赛各占一支色系且两套主题都不混：除了各自落在

>   补班的蓝更必须与休假的红离得最开（§8.1）；假期那档到 25° 为止，穿不上节日那支琥珀。
>   色值可以调，类别不能对调（`calendar/cell-visual-contract.test.ts` 的「语义色按类别分色」）；
> - **小徽标规则扩到「补」**——§7.3 与 §8.2 是同一条规则，DOM 上按两种字各查一遍
>   （`calendar/MonthView.test.tsx` 的对应用例），唯一载体是右下角那一个大字。

> **SC-018 的结单（2026-09-25）**：设置页的画面（七节、两套主题、侧栏与详情栏留位）
> 在实现落地时已有人工验收，本轮补的是五条验收措辞里**没有守卫**的部分——它们此前
> 只有零散用例，改坏不一定有测试变红：
>
> - **所有 v0.1 偏好可持久化**——注册表从源码的 `export const *_SETTING_KEY` 收集（当前 8 条：
>   7 条偏好 + 提醒去重日志），每条都要有写入路径、启动读取与读 / 归一化边界，缺哪件都会被
>   `settings/settings-contract.test.ts` 报出来（只写不读＝「看起来设过、其实不生效」，只读不写＝改不动）。
>   键名不许写死在调用点上：`App.tsx` 只接受 `*_SETTING_KEY` 常量与两个登记过的例外。
>   启动读回此前缺两半——`notifications.enabled` 没有 App 级证据、`webcal.refreshIntervalMinutes`
>   只测了「坏值回落默认」，两者都由 `App.test.tsx` 补齐（关掉通知的订阅到点不弹、间隔 60 分钟
>   直接进设置页而不是被改写成 6 小时）。**写 → 重启 → 读**的完整一圈由一条用例走完：七条偏好各改一次，
>   把最后写下的快照交给下一次启动，逐项恢复（主题在装配层就恢复，其余在设置页里核对）；
> - **设置改动即时生效或明确提示需重启**——写偏好的 handler 必须同时有落盘与即时效果。
>   通知与比赛提醒的即时性**不是** handler 里那句 `reschedule()` 提供的：那句先按旧计划排一次
>   （当时状态还没变），真正让新设置生效的是随后由状态变化触发的计划重建（`rebuildReminderPlan`
>   与它的 effect，见 [app-spec.md](app-spec.md) §SETTINGS 的结单口径）；因此端到端证据是
>   「改完在本次会话里就按新计划重排」：关掉「日历提醒」后 23:00 不弹、重新打开立即恢复；
>   把「比赛提醒」从 30 分钟改成 15 分钟后，23:00 不再弹（旧计划已被换掉）、23:15 按新提前量弹出。
>   另一半（“或明确提示需重启”）今天不成立也不需要：没有需要重启的设置，因此有用例盯着设置页
>   不出现「重启」字样——真加上那样一条设置时，这条断言要被换成一条真提示；
> - **数据源启停不删除用户数据**——订阅一侧早有「停用后事件仍在快照里」的用例，本地导入一侧本轮补齐
>   （停用后事件与来源都留在快照、重新显示不需要重新导入）；反向的牙也验过：把它改成停用即删事件，用例立刻变红；
> - **设置页面不演变为 Dashboard**——两层守卫。源码层：`layout/SettingsView.tsx` 的 import 收成白名单
>   （偏好规则、展示原语、只借类型的载荷），事件数据与派生层进不来，白名单每项写明理由且必须仍被使用；
>   运行期：七节清单逐字相等（新增一节就变红），且设置页里的事件文本只允许出现**一处**、必须是「下一条提醒」那一行
>   ——§12 的可解释状态，不是事件列表。这一条顺带纠正了一个想当然的写法：起初想断言「设置页不出现事件标题」，
>   而「下一条提醒：… Arsenal vs Manchester City」是 §12 明确要求的；现在锁的是它只出现一次、且只在状态行里；
> - **对网络源显示最近刷新状态**——`layout/source-display.test.ts` 把取值域逐条钉住（尚未刷新 / 上次成功 /
>   刷新中 / 已停用 / 失败 + 上次成功，以及「有 error 无原因」这种只可能来自手改快照的边界不写空话），
>   当时 `App.test.tsx` 要求**设置页与侧栏渲染出逐字相同的状态**（成功与失败各一次；脱敏在落库前完成，
>   两边都只是照读）——两处共用 `layout/source-display.ts`，这条断言就是「说法不会各自漂移」的守卫。
>
> 本轮 13 处「改坏它、看它变红」都逐一验过：启动读取（比赛提醒 / 通知开关 / 刷新间隔 / 主题各一次）、
> handler 只落盘不应用（通知开关、比赛提醒）、handler 全无即时效果（主题）、字面量键名、设置页的越界 import、
> 来源状态文案改写、设置页多出第八节、设置页自造的来源状态文案、停用即删数据。守卫的牙也写进了各自的
> 测试文件（`settings/settings-contract.test.ts` 的「守卫的牙齿」一组覆盖声明形态、调用点实参、handler 写法
> 与 import 白名单）。另顺手把三处 CRLF 工作区副产物还原成仓库的 LF 形态；没有生产行为改动。

## 6. 复现方式

### A. 不需要数据（主题、假期、节气、折叠、最小窗口）

```bash
cd apps/desktop
npm run dev
```

浏览器打开 `http://localhost:1420/`，用主导航切到 2026 年 10 月（国庆连休与补班）、
点侧栏「设置」→「外观」切深色、点左右栏底部的「收起」、把窗口缩到 820×560。
无桌面壳时状态行会写明「浏览器预览模式：本地数据层仅桌面壳可用」，属预期。

### B. 需要数据（比赛格与比赛详情）

```bash
cd apps/desktop
npm run tauri -- dev
```

在桌面窗口里打开设置，使用「导入 ICS 文件…」导入 §2 的 ICS，切到对应月份并点击比赛日。
比赛日视觉与 Matchday Inspector 需要事件数据，浏览器预览模式下没有本地数据层，
因此这一组必须在桌面壳里做。
