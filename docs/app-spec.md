## 1. 产品定义

Semantic Calendar（语义日历）是一款 **本地优先、轻量常驻、能够理解事件语义的桌面日历**。

它首先必须是一个可靠的日历，其次才是一个“语义增强”日历。

核心命题：

> 日历不仅知道“什么时候发生”，也尽量知道“发生的是什么”。

例如：

- `Arsenal vs Manchester City` 不只是文本，而是“英超比赛 + 两支球队 + 比赛时间 + 可提醒事件”；
- “中秋节”不只是全天事件，而是传统节日；
- 国庆假期应在月视图中表现为连续休假，而不是若干无关文本；
- 补班、节气、赛事在视觉上应有不同语义，但都不能破坏普通日历体验。

---

## 2. v0.1 成功标准

v0.1 完成时，用户应能：

1. 启动一个可长期常驻的桌面日历；
2. 在月视图浏览、切换和选择日期；
3. 导入本地 ICS，并订阅 ICS / WebCal；
4. 正确处理全天事件、重复事件、时区和 UID 去重；
5. 看到中国农历、法定节假日、调休 / 补班、传统节日和二十四节气；
6. 自动识别常见英超比赛标题；
7. 在月格看到联赛 / 球队语义视觉，在右侧查看完整比赛详情；
8. 关注一支球队并获得可配置的赛前提醒；
9. 在浅色 / 深色主题间切换；
10. 在离线或数据源失败时仍能浏览已缓存日历；
11. 在 Windows 上稳定打包运行；
12. 有可重复的性能基线和核心测试。

## 3. 明确不属于 v0.1

v0.1 不做：

- Google Calendar / Outlook 双向同步；
- CalDAV 完整同步；
- 团队协作；
- 邀请与会议室管理；
- Calendly 类预约排程；
- Todo / 项目管理系统；
- 新闻流、体育资讯流；
- AI 作为基础识别依赖；
- 账号系统优先的云端 SaaS；
- 插件商店；
- 多体育项目全面覆盖；
- 移动端；
- 复杂社交功能。

这些能力不能阻塞 v0.1 的核心垂直链路。

## 4. 目标用户与核心任务

### 4.1 目标用户

主要面向：

- 希望桌面日历长期常驻但不想承担高资源占用的个人用户；
- 使用 ICS / WebCal 订阅多个来源的用户；
- 希望中国日历信息自然融入月视图的用户；
- 希望体育赛程在普通日历中更好识别的用户。

### 4.2 核心任务

用户打开应用后最常做的事情应当是：

1. 看这个月；
2. 识别近期特殊日期；
3. 点击某一天查看详情；
4. 导入 / 订阅日历；
5. 查看关注球队比赛；
6. 接收提醒；
7. 切换主题和数据源。

## 5. 产品原则

### P-01 日历可靠性高于语义增强

Matcher 失败时必须回退为普通事件，不能让事件消失。

### P-02 本地优先

能在本地完成的解析、匹配、元数据解析和存储应默认本地完成。

### P-03 确定性优先

节假日、节气、球队和结构化比赛优先使用规则与结构化数据，不把 AI 作为必需依赖。

### P-04 语义与展示分离

“这是什么”与“怎么显示”必须分层。

### P-05 月历是主界面

v0.1 不增加 Dashboard 首页。

### P-06 可解释的网络行为

用户应知道某个网络数据源是否更新成功、何时刷新、失败原因是什么。

### P-07 轻量常驻

性能预算从第一版开始记录，不把性能推迟到发布前。

## 6. 信息架构

桌面主界面采用三栏：

```text
Sidebar | Calendar | Inspector
```

### Sidebar

负责：

- 小月历；
- 数据源显示开关；
- 关注球队；
- ICS 导入；
- 设置入口。

### Calendar

负责：

- 月 / 周 / 日入口；
- v0.1 重点实现月视图；
- 日期导航；
- 事件 / 特殊日期语义展示；
- 日期选择。

### Inspector

负责：

- 当前日期详情；
- 当前事件详情；
- 节日 / 节气详情；
- 体育比赛详情。

Inspector 不是固定“今日安排”面板。

完整视觉规范见 [ui-design.md](ui-design.md)。

## 7. 系统架构

主数据链路：

```text
Calendar Sources
  ↓
Source Adapters
  ↓
Event Normalizer
  ↓
Matcher Engine
  ↓
Semantic Event
  ↓
Metadata Resolver
  ↓
Persistence / Calendar UI / Notifications
```

### 7.1 Calendar Sources

v0.1：

- 本地 ICS 文件；
- ICS / WebCal URL；
- 中国日历内置 / 更新数据；
- 英超结构化数据或可替换 Provider。

### 7.2 Source Adapters

把来源不同的数据转换成统一 Raw Event。

### 7.3 Normalizer

处理：

- Unicode；
- 标题常见格式；
- 全天事件；
- 时区；
- UID；
- 重复事件；
- recurrence 展开 / 解释；
- 原始字段保留。

### 7.4 Matcher Engine

负责识别：

- 节假日；
- 传统节日；
- 节气；
- 足球比赛。

> 当前实现（SC-009 / SC-011 / SC-012）：引擎的输入是事件（`NormalizedEvent`），因此只有“事件语义”走这里——足球比赛标题识别（SC-015）注册为 `priority` 100 起的 Matcher。日期本身的属性（法定节假日 SC-011、传统节日与节气 SC-012）装不进事件引擎：同一天可以有任意多事件，也可以一个都没有，而“这一天在放假”与有没有事件无关。这类**日级语义**与农历一样以日期键为入口（SC-011 为 `providers/china/holidays.ts` + `semantic/app-china-days.ts`，SC-012 为 `providers/china/festivals.ts` / `solar-terms.ts` + `semantic/app-china-festivals.ts`），`priority` 0–99 区间保留给按日期判定的事件语义。两条路径都遵守同一条边界：识别归 Provider / Matcher，展示元数据归 Resolver，UI 不判断。

### 7.5 Metadata Resolver

负责：

- 本地化名称；
- 联赛 / 球队元数据；
- 图标 / Logo 资源引用；
- 语义颜色；
- 默认提醒策略。

> 当前实现（SC-009 / SC-014）：组合器按注册顺序取第一个非 null 结果。核心只定义展示契约（`accent` / `label` / `iconRef` / `reminder` / `fixture`），内容全部来自 Provider——足球赛事的 `fixture` 载荷（联赛 + 双方展示信息 + 队徽引用）由 `providers/football/` 提供，UI 只读取收窄后的载荷，不做任何球队判断。
>
> 日级语义不走这条链（见 §7.4）：休假 / 补班、传统节日与节气的资源引用随日级载荷给出（`backgroundRef`），由 `semantic/day-backdrop.ts` 解析；`iconRef` 因此仍然留给「挂在事件上的语义」，当前没有 Provider 填充。

### 7.6 UI

UI 不允许通过 `title.includes(...)` 自行判断业务语义。

## 8. 核心数据模型

实现阶段字段可调整，但语义边界应保持。

### 8.1 CalendarSource

```ts
type CalendarSource = {
  id: string
  type: 'local-ics' | 'webcal' | 'builtin' | 'provider'
  name: string
  enabled: boolean
  color?: string
  lastSyncAt?: string
  lastSyncStatus?: 'ok' | 'error' | 'never'
}
```

### 8.2 RawCalendarEvent

```ts
type RawCalendarEvent = {
  uid: string
  sourceId: string
  title: string
  description?: string
  location?: string
  start: string
  end?: string
  allDay: boolean
  recurrence?: unknown
  rawPayload?: string
}
```

### 8.3 NormalizedEvent

```ts
type NormalizedEvent = RawCalendarEvent & {
  normalizedTitle: string
  timezone?: string
  occurrenceId?: string
}
```

### 8.4 SemanticEvent

```ts
type SemanticEvent = {
  type:
    | 'calendar.event'
    | 'holiday'
    | 'makeup-workday'
    | 'festival'
    | 'solar-term'
    | 'sport.fixture'
  subtype?: string
  entities?: Array<{ type: string; id: string }>
  confidence?: number
  matcherId?: string
}
```

> 两处来源（SC-011）：`calendar.event` 与 `sport.fixture` 由事件 Matcher 产出，语义挂在事件上（§7.4）；`holiday` / `makeup-workday`（以及 SC-012 的 `festival` / `solar-term`）是**日级语义**，由日期 Provider 产出、以日期键为入口，不挂在任何事件上——因此 `metadata-resolver.ts` 里这些类型的内置默认值（语义色 / 短标签 / 默认提醒）服务于日级展示，不是事件增强的兜底。

### 8.5 EnrichedEvent

```ts
type EnrichedEvent = NormalizedEvent & {
  semantic?: SemanticEvent
  metadata?: Record<string, unknown>
}
```

原始事件必须可以追溯。

## SRC — 数据源

### SRC-001 本地 ICS

支持用户选择本地 `.ics` 文件并导入。

### SRC-002 WebCal / ICS URL

支持添加 URL、手动刷新与后台低频刷新。

> 当前实现（SC-007）：地址归一化（`webcal://` → `https://`、缺协议补 `https://`、去 fragment）与校验在 `data/webcal/webcal-url.ts`；抓取经 Rust 命令 `webcal_fetch`（条件 GET，带 `If-None-Match` / `If-Modified-Since`，连接超时 10s、总超时 30s、正文上限 20MB）；刷新策略的常规间隔是设置项 `webcal.refreshIntervalMinutes`（SC-018，默认 6 小时），失败后固定 30 分钟重试，只维护一个指向最近到期时刻的定时器（`data/webcal/refresh-scheduler.ts`），不使用 `setInterval`——间隔可调，调度的形状不变。

### SRC-003 数据源状态

至少记录：

- 是否启用；
- 上次成功刷新；
- 上次错误；
- 来源类型。

> 当前实现（SC-007）：`CalendarSource` 增加可选 `webcal` 分区（订阅地址、ETag / Last-Modified、`lastCheckedAt`）。`lastSyncAt` 只在成功刷新（含 304）时推进，失败时保留上次成功时间；错误文案落库前脱敏，不写入 URL token（§14）。

### SRC-004 离线缓存

网络来源不可用时继续显示本地缓存结果。

> 当前实现（SC-007）：抓取失败（网络、超时、HTTP 错误、内容无法解析、空内容）只标记来源状态，不删除该来源已入库的事件；空日历在已有缓存时按失败处理并保留缓存（服务端维护页 / 代理空壳与真正清空的订阅无法区分，P-01 优先保证不丢数据）；304 表示本地缓存仍然有效，事件与增强结果都不变。

## ICS — 解析可靠性

### ICS-001 UID

同一来源内按 UID / recurrence identity 避免重复导入。

### ICS-002 全天事件

全天事件不能因为时区转换漂移到前一天 / 后一天。

### ICS-003 时区

支持常见 TZID / UTC / 本地时间组合。

### ICS-004 重复事件

支持 v0.1 常见 RRULE，并能处理 EXDATE / RECURRENCE-ID 的基础场景。

### ICS-005 错误隔离

一个损坏事件不能导致整个日历源无法导入。

## SEM — 语义框架

### SEM-001 Matcher 注册

Matcher 必须可独立注册并有确定优先级。

### SEM-002 MatchResult

结果至少包含：

- semantic；
- matcherId；
- 可选 confidence；
- 可选 reason。

### SEM-003 回退

没有匹配时按普通事件显示。

### SEM-004 重新匹配

保留原数据，使 Matcher 更新后可重新计算语义，无需重新下载源数据。

## CN — 中国日历

### CN-001 农历

月格显示农历日；必要时显示月份边界。

实现口径（SC-010）：月格在初一显示农历月名（「八月」「闰四月」）——初一就是农历月份边界，写月名同时表达日期与边界，闰月也不会退化成普通月份；其余日期显示农历日名（「初二」…「三十」）。详情栏显示完整写法（「农历八月廿七」）。农历数据按年维护，覆盖范围之外安静地不显示。

### CN-002 法定节假日

显示法定休假。

### CN-003 调休 / 补班

显示补班，并与休假视觉明确区分。

### CN-004 连休

连续假期在 UI 上形成连续视觉。

实现口径（SC-011）：休假与补班是两种语义（`rest` / `makeup`），由 `providers/china/holidays.ts` 按日期键统一输出，UI 拿到的是「类别 + 语义大字 + 假期名 + 连休位置」；补班日不带连休区段，因此两者不可能被渲染成同一种状态。连休分组在 Provider 侧完成：同一次假期里连续放假的日期共享一个区段（`run.id` 取区段首日，`index` 从 0 起，`length` 为天数），相邻日期格拿到相同 id 就能画成 §7.1 要求的连续视觉，UI 不需要自己扫相邻格。月格的休假视觉（连续背景、被格子裁切的「休」「补」大字、多语义冲突规则）属 SC-013；SC-011 交付文字层（详情栏的「国庆节假期 · 第 3 天 / 共 7 天」「国庆节补班日」）。

### CN-005 传统节日

首批至少支持常见传统节日，如春节、中秋等。

实现口径（SC-012）：节日表 `providers/china/festivals.ts` 只登记日期无争议的节日——春节、元宵节、龙抬头、清明节、端午节、七夕、中元节、中秋节、重阳节、腊八节、除夕。判定规则只有三种历法事实，不抄日期表：农历固定月日；农历年的最后一天（除夕：腊月 29 还是 30 天由年数据决定，不写死廿九 / 三十）；节气日（清明节＝清明，与 CN-006 共用同一张表）。闰月不算节日（闰五月初五不是端午）。小年（北方廿三 / 南方廿四）与寒食（清明前一二日）的日期随地区与流派变化，不登记、也不猜一个（P-03）。

同日多条语义是刻意的：清明节当天既是传统节日，又是节气，还可能是法定节假日（SC-011），三条都成立；月格只画一个主背景（§16.1 的优先级由 SC-013 落实）。节日名占月格里农历那一行（ui-design 参考图：特殊日期用语义内容取代农历简写），详情栏是名称 + 英文名 + 一句释义；文本规则在 `providers/china/festival-labels.ts`，UI 接线在 `semantic/app-china-festivals.ts`。

### CN-006 二十四节气

显示节气名称与对应日期。

实现口径（SC-012）：日期表 `providers/china/solar-terms-data.ts` 由 `tools/derive-solar-terms.mjs` 从香港天文台「公曆與農曆日期對照表」年表的「節氣」列推导（与农历表 lunar-data.ts 同一批文件、同一来源口径），覆盖公历 1901–2100：每个公历年 24 个日期，节气与月份的对应是固定的（小寒 / 大寒在一月……冬至在十二月），因此只存日、不存月。节气日期没有可用的简单公式，只有天文数据；表外年份安静地不显示，不推算（P-03）。可更新策略：表只由推导工具生成，范围扩展或数据修正时重跑工具并补官方样例（与 CN-007 的节假日数据同一条口径：数据可追溯、不手改）。

查询在 `providers/china/solar-terms.ts`（节气名与序号），文本与背景引用在 `solar-term-labels.ts`：月格右上角是节气名小标签，详情栏是名称 + 英文名 + 序号（「第 19 个节气」）+ 一句释义（ui-design §9.2）。专属背景是逻辑引用（`bg.solar-term.cold-dew`），仓库不分发图片二进制，由资源包经 `semantic/day-backdrop.ts` 解析，取不到就是没有背景——节气名与释义照常显示。SC-022 的结论是 v0.1 不接入照片资源（没有可随应用分发的图片许可），因此专属背景在默认构建里不会出现图片，只保留能力；决定与将来接入的条件见 [third-party-assets.md](third-party-assets.md) §1、§3。UI 接线在 `semantic/app-china-festivals.ts`。

### CN-007 年份数据

节假日数据需要有年份版本与可更新策略。

实现口径（SC-011）：数据按**通知年份**逐条登记（`providers/china/holidays-data.ts`），每条带上通知文号、发布日期与原文地址，以及本仓库内的 `revision`（只改数据不改年份时递增）。查询结果里每一天都带 `version`，可回溯到具体发文。可更新策略：国务院办公厅发布下一年度通知后，追加一条安排并补测试样例（放假天数、农历互证日期）；`revision` 只在修正既有年份的数据时递增。没有登记安排的年份安静地不显示休 / 补，不推算（P-03）——放假安排没有公式，只有发文。

## SPORT — 体育 / 英超

### SPORT-001 英超球队元数据

支持 20 支参赛球队的：

- 稳定 ID；
- 中英文名称；
- 常见别名；
- Logo 引用；
- 主题元数据。

赛季变化不能要求重写 Matcher。

> 当前实现（SC-014）：球队字典 `apps/desktop/src/providers/football/teams.ts` 保存 20 支球队的稳定 ID、中英文名、常见别名、3 字母代码、近似球队色与 `crestRef` 逻辑引用；联赛元数据与赛季参赛名单在 `competitions.ts`（名单是独立数据条目，新赛季追加即可，Matcher / Resolver / UI 不改）；装配与查询在 `football-catalog.ts`，装配期校验球队与联赛别名唯一、已规范化且不冲突，坏数据直接抛错。
>
> Logo 边界：仓库不分发球队徽标与联赛 Logo 二进制，元数据只保存逻辑引用；引用缺失、资源包未收录或资源包抛错时，`semantic/marks.ts` 一律降级为 fallback（3 字母代码 / 联赛短标签 + 主题色）。SC-022 定下的 v0.1 口径是**不随应用分发任何徽标二进制**（商标不属于可自由分发的素材），因此默认构建恒走 fallback；将来接入资源包必须满足的条件见 [third-party-assets.md](third-party-assets.md) §3。（解析规则 SC-016 起位于核心：它针对的是核心展示契约 `FixtureDisplay`，而 UI 不能 import Provider 目录——月格与 Inspector 都要渲染标记。）
>
> 名单口径：只登记已确认的完整参赛名单，当前为 2025/26；“最新赛季”指已登记名单中最新的一季，不代表“今天正在进行的一季”。

### SPORT-002 比赛识别

识别常见标题：

- Arsenal vs Manchester City
- Arsenal - Manchester City
- Manchester City @ Arsenal
- 大小写 / 多余空格等变体

> 当前实现（SC-015）：`apps/desktop/src/providers/football/football-matcher.ts` 用 SC-014 目录给出的词表（别名 + 中英文规范名 + 联赛写法）单趟扫描标题，判定链为：
>
> 1. 恰好两支可确定归属的球队；
> 2. 两队之间是一个已知对阵分隔符（`vs` / `vs.` / `v` / `v.` / `versus` / `-` / `–` / `—` / `@` / `对`）；
> 3. 标题除“两队 + 分隔符 + 联赛名 + 装饰”之外没有别的单词；
> 4. 联赛可确定：标题写明已登记联赛就用它，否则要求两队同属某个已登记赛季名单——两种情形都必须在名单里找到两队，拿不到证据就不增强（P-03）。
>
> 第 3 条是“不误伤”的关键：只要求“两个词表里的球队 + 一个分隔符”时，一次展览（`Kensington Palace - Chelsea Flower Show`）或一趟火车（`Brighton - Leeds train`）都会被判成比赛——它们的两侧不是球队名，而是包含球队名的短语。允许的装饰只有 `标签: ` 前缀（`Premier League: `、`Matchday 12: `、`英超：`）与联赛名本身；括号不构成豁免，括号里的词同样要能被解释（联赛名，或纯标点），否则 `Brighton - Leeds (train)` 这类括号备注又会漏进来。代价是标题带自由文本时会漏判（`… - Matchday 12`、`(Emirates Stadium)`）——刻意取舍：漏判只是少一次增强，误判会给普通事件挂上英超徽标。
>
> 其余不增强的情形：多于两支球队、同一支球队出现两次、比分（`Arsenal 3-1 Manchester City`）、没有分隔符、对手不在字典里（`Arsenal vs Barcelona`）、明显非足球标题。事件按普通事件显示（SEM-003）。
>
> 可解释性：判定依据写进 `MatchResult.reason`（如「vs」左侧为主队；按 2025/26 名单推断联赛，引号里是标题里实际出现的分隔符），`confidence` 取两项证据里较弱的一项——联赛明示 1 / 名单推断 0.8，方向明示（`@`）1 / 赛程惯例 0.9。
>
> 边界：v0.1 只登记英超，“两队都在英超名单内”即认定为英超比赛——两支英超球队的杯赛（如足总杯）在 v0.1 也会标为英超；多联赛支持是 SPORT-001 的扩展点（登记新联赛与名单后判定链自动适用）。3 字母代码（`ARS` / `MCI`）刻意不进词表：`EVE` / `SUN` / `NEW` 这类代码在普通标题里会误命中（P-03）。

### SPORT-003 主客队

尽可能识别 home / away。

不确定时允许保持未知。

> 当前实现（SC-015）：主客队用 `SemanticEvent.entities` 的顺序表达——第 0 个是主队、第 1 个是客队，这正是 SC-014 Resolver 渲染 `fixture.teams` 所依赖的接口。`A @ B` 明示 A 客场作战（B 为主队）；`A vs B` / `A - B` 按赛程列表惯例左侧为主队。
>
> 与“不确定时允许保持未知”的关系：entities 顺序本身就是主客顺序的接口，没有“方向未知”的第三种状态，因此方向无法判断时（没有分隔符、多于两支球队）不增强，而不是给一个猜出来的顺序（宁可暂缺，也不给出错误事实）。方向只靠惯例时 `confidence` 低于 1，`reason` 写明依据——让“这是惯例推断”可解释，而不是被当成明示事实。

### SPORT-004 比赛月格

月格只显示：

```text
队标 VS 队标
```

以及被裁切在格内的联赛背景视觉。

> 当前实现（SC-016）：`apps/desktop/src/calendar/MatchCell.tsx` 渲染“队标 VS 队标”，`MatchCellBackground` 渲染联赛背景；队名、开赛时间、球场、天气、提醒都不进格子（ui-design §10.2）。背景层是日期格的直接子元素，格子的 `overflow: hidden` 负责裁切，因此背景可以很大却不会溢出到相邻日期格（§10.1）；一天多场比赛时每格只画一次背景，单格最多显示两场，其余折叠为“还有 N 场比赛”。
>
> 判定依据是 `metadata.fixture` 是否存在（Resolver 是否给出完整对阵载荷），而不是 `semantic.type`：载荷残缺时事件留在普通摘要通道，不会渲染出缺一侧的半张比赛卡（`calendar/event-display.ts` 的 `splitFixtureEvents`，月格与 Inspector 共用）。同日普通事件照常显示为摘要——比赛是状态语义，不吞掉其他语义。
>
> 队徽 / 联赛 Logo 渲染在 `display/Mark.tsx`：固定容器 + `object-fit`，资源缺失降级为球队代码 / 联赛短标签 + 主题色（容器色取自球队 / 联赛色，文字取主题前景色，深浅主题都可读）。

### SPORT-005 比赛 Inspector

至少显示：

- 联赛；
- 两队；
- 队徽；
- 开赛时间；
- 场地（有数据时）；
- 天气（有可靠来源时）；
- 提醒。

> 当前实现（SC-016）：`apps/desktop/src/layout/MatchdayInspector.tsx`，由 `InspectorPanel` 在当日存在完整对阵载荷时进入比赛模式（星期行追加 `MATCHDAY`，整栏换成赛事氛围背景，ui-design §13–15）。层级：日期 / 对阵双方 / 队徽（一级），联赛 / 开赛时间（二级），场地 / 提醒（三级）；当日其余事件作为状态语义留在下方。
>
> 缺字段就不渲染该行（不填占位、不给默认值）：**天气在 v0.1 没有可靠来源，因此这一行从不出现**；场地取自来源事件的 `LOCATION`，用“场地”而不是“主场”表述——`LOCATION` 是事件地点，未必等于主队球场；全天比赛没有开赛时间，不渲染开赛行；提醒文案由 Resolver 的提醒策略翻译（`format/reminder.ts`，SC-017 复用同一策略），标题写成“建议提醒”——NOTIFY-003 说的是“比赛可建议赛前 30 分钟”，它是策略建议而不是事件自带的数据，不能写成事实陈述。
>
> 主题：浅色用降低饱和度的蓝灰渐变 + 左缘柔和过渡（§14 “它是主界面的一部分”），深色用深蓝渐变与联赛水印（§15.4），信息架构完全一致，差异全部由 `--bg-matchday-*` 变量承担。联赛水印与月格背景共用 `display/CompetitionBackdrop.tsx`：有资源时是 Logo，没有或加载失败时是联赛短标签字形。

### SPORT-006 关注球队

用户可选择关注球队。

关注球队状态需要持久化。

> 当前实现（SC-016）：关注状态是稳定球队 id 列表（设置键 `football.followedTeams`），不保存任何展示字段——球队改名 / 换色 / 换队徽不需要迁移。规则在 `providers/football/followed-teams.ts`，由 `semantic/app-followed-teams.ts` 绑定到应用目录后暴露给 UI（UI 不 import Provider 目录）；侧栏选择器 `layout/FollowedTeamsPicker.tsx` 列出最新赛季名单，勾选即由 `App` 写入本地数据层，重启后从设置恢复。读取边界只接受目录认识的 id，坏值（非数组、数字、未登记球队、带空白的写法）一律丢弃，不猜成某支球队（P-03）；列表统一规范化到名单顺序。
>
> 可见效果：比赛详情里对应球队带“关注”标记。月格不因关注改变（§10.2 只显示队标 VS 队标），赛前提醒由 SC-017 消费同一份关注状态；设置页入口（含关注球队）由 SC-018 接线。
>
> 边界：赛季名单更新时，已不在名单内的球队会同时从可关注集合与关注列表消失——这是名单登记的显式后果（只在登记新赛季时发生），不是运行期静默丢数据。

## NOTIFY — 提醒

### NOTIFY-001 本地通知

应用可以创建系统本地通知。

### NOTIFY-002 事件提醒

普通事件可按事件自身 alarm 或用户设置提醒。

### NOTIFY-003 比赛默认提醒

比赛可建议“赛前 30 分钟”，但用户设置优先。

### NOTIFY-004 去重

应用重启 / 数据刷新不得重复触发同一个提醒。

> 当前实现（SC-017）：通知链路的“什么时候弹”与“怎么弹”分开——`apps/desktop/src-tauri/src/notify.rs` 只回答权限状态并发送一条通知（webview 不直接接触通知 API），`apps/desktop/src/notifications/` 负责提醒时间计算、去重与调度。一条提醒的来源按 **用户设置 ＞ 事件自带 VALARM ＞ Resolver 默认建议** 取（NOTIFY-002 / NOTIFY-003）；提醒的稳定键 = 事件持久化身份 + 依据 + 触发时刻，因此订阅刷新与重启都会重建出同一个键而不重复弹（NOTIFY-004），事件改期后触发时刻变化则是一条新提醒。事件自带提醒在解析层从 VALARM 读出（`ics/parse-ics.ts` → `RawCalendarEvent.alarms`）：只接收相对时间的 TRIGGER 与 `ACTION:DISPLAY`，绝对时间 TRIGGER 与 EMAIL / AUDIO 动作不产生本地提醒。设置项为 `notifications.enabled`（默认开启）与 `notifications.matchReminderMinutes`（未设置 = 跟随建议；数字 = 用户提前量；`null` = 不提醒），界面上“跟随默认建议（赛前 30 分钟）”里的数字直接来自 Resolver，没有第二份默认值。完整实现说明见 README「本地通知与提醒调度（SC-017）」。

## SETTINGS — 设置

v0.1 设置至少覆盖：

- 主题；
- 数据源；
- WebCal 刷新；
- 关注球队；
- 通知开关；
- 默认比赛提醒；
- 基础语言 / 区域预留。

设置界面保持轻量，不做多层复杂后台。

> 当前实现（SC-018）：设置是一个页面而不是新的首页——它取代月历主区域的位置，顶部有「返回月视图」，侧栏与详情栏留在原处，打开状态不持久化（月历是主界面，P-05）。页面分七节：**外观**（浅色 / 深色分段控件，选中即生效并写入 `app.theme`）、**区域**（预留：只陈述当前固定取值「简体中文 / 周一起始 / 跟随本机时区」，不写入任何设置键——写一个没有读取方的值只会让快照出现假状态）、**数据源**、**关注球队**、**通知**（`notifications.enabled` 与 `notifications.matchReminderMinutes`）、**关闭窗口时**（`app.closeBehavior`）、**关于**（SC-022：只读的名称 / 版本 / License，不写入任何设置键）。所有控件即时生效，没有需要重启的选项，因此界面也不写“需要重启”。
>
> 数据源一节承担「管理」：内置来源的显示开关（`sources.builtinHidden`，只记被隐藏的 id，缺省全开，将来新增内置来源不需要迁移旧快照）、导入 / 订阅来源的最近刷新状态与删除入口（删除前确认，级联删除该来源的事件）、WebCal 刷新间隔（`webcal.refreshIntervalMinutes`，选项 1 / 3 / 6 / 12 / 24 小时，默认 6 小时；不在选项内的快照值按默认处理，不猜）。
>
> 关闭不删数据：内置来源的开关只影响展示——「我的日历」关闭后用户事件不进月视图（月格只留内置语义日期），「中国节假日」关闭后休 / 补语义与假期底色消失，「二十四节气」关闭后传统节日与节气语义消失，「英超赛程」关闭后比赛按普通事件进入月格、详情栏**与提醒计划**（与 SEM-003 同一口径，见 `semantic/app-builtin-sources.ts`）。过滤掉的是视图字段（`semantic` 与展示元数据）而不是数据：识别结果仍写在快照的增强分区里，重新打开立即恢复、不需要重新匹配；连 `semantic` 一起摘是因为提醒计划先看 `semantic.type` 再回落到事件自带 VALARM——只摘展示元数据的话，用户设置过的“比赛提醒”仍会弹，与界面的承诺矛盾。四行开关与 ui-design §4.3 的数据源行同名同序，侧栏与设置页读写同一份设置（一处状态、两个入口）。
>
> 刷新间隔由供应商注入调度器（`intervalMs`），改设置后 `reschedule()` 立即按新间隔重排，不需要重建调度器；失败重试间隔固定 30 分钟，与这条设置无关（失败来源需要更快恢复）。关注球队在这一页与侧栏共用同一个选择器组件与同一份状态。完整实现说明见 README「设置页与内置来源开关（SC-018）」。

## 10. UI 语义规则

完整规则以 [ui-design.md](ui-design.md) 为准。

必须保证：

- 连休背景连续；
- 假日使用大号低透明度“休”，不再重复小“休”徽标；
- 补班使用蓝色语义 + 大“补”；
- 特殊节日 / 节气可有受控背景图片；
- 比赛日联赛图形不得溢出日期格；
- 比赛格只显示队标 VS 队标；
- 多语义冲突遵循“一个主背景语义 + 多个状态语义”；
- 右栏为 Inspector；
- 浅色赛事 Inspector 与主界面自然融合；
- 深色主题保持相同信息架构。

> 当前实现（SC-013）：月格的主背景由 `apps/desktop/src/calendar/cell-backdrop.ts` 裁决，一个格子只有一个——节日 / 节气专属视觉 ＞ 联赛视觉 ＞ 假期 / 补班（底色 + 大「休」「补」）＞ 普通背景（§16.1 优先级）。假期视觉是其中一个候选而不是叠加层：§7.2 / §8.2 把大字定义为背景元素，参考图里 10 月 4 日（休假 + 比赛）只画狮标与队标 VS 队标、10 月 6 日（节日 + 休假）只画节日视觉，因此主背景被拿走的那些日子不再单独画底色或大字，一个格子不会同时出现狮标、队标与一个巨大的「休」（§26「多语义不会堆叠失控」）。比赛对阵块与事件摘要是两条不参与竞争的叠加，与任意主背景共存。
>
> 底色是「语义色混进主题底板」（浅色 13%；深色 22% 混进更暗的底板，即 §15.2 的暗红 / 暗蓝），落在格子底板上而不是单独一层，所以 hover、选中（§17）与跨月弱化都能叠加在它之上，而不是把语义背景覆盖掉。连休的连续性由同一次假期里每一天的同一支底色表达（§7.1 / CN-004）；某一天让位给节日或比赛时，该日不放假的说明由详情栏承担（SC-011 的「国庆节假期 · 第 3 天 / 共 7 天」）。
>
> 「休」「补」大字是格子的直接子元素，由格子的 `overflow: hidden` 裁切，因此只会被切掉、不会溢出到相邻格；文字层（日期数字、农历、语义名、事件、比赛块）整体压在背景层之上，大字不遮挡日期数字。参考图里的右上角小徽标按 §7.3 不再出现——一个月格最多只有一个「休」或「补」。
>
> 节日 / 节气背景是逻辑引用（`bg.festival.*` / `bg.solar-term.*`）经 `semantic/day-backdrop.ts` 解析出的图片：整格铺满、`object-fit: cover`、降饱和，文字区带遮罩（§9.1），深色主题再压暗一档（§15.3）；资源缺失或图片加载失败就是不画背景，日期与语义文字照常显示。应用装配不传资源包，专属背景只具备能力、不出现图片——这是 SC-022 定下的 v0.1 口径（没有可随应用分发的图片许可），见 [third-party-assets.md](third-party-assets.md) §1。
>
> 裁切、层级与两套主题的取值无法在 jsdom 里验证，因此写成 `calendar/cell-visual-contract.test.ts` 对 `index.css` 的可执行断言；主背景优先级、大字唯一性、连休同色与多语义组合由 `calendar/cell-backdrop.test.ts` 与 `calendar/MonthView.test.tsx` 覆盖。

## 11. 持久化需求

v0.1 推荐 SQLite 或等价轻量本地数据库。

> 当前实现（SC-003）：采用版本化 JSON 快照 `store/calendar-store.json` 作为“等价轻量数据库”——schema v1、迁移链、原始/增强数据分离、损坏隔离恢复、原子写。存储接口按可替换 SQLite 适配器设计；待事件量达到性能基线测量（§15）后评估是否切换。

需要持久化：

- CalendarSource；
- Raw event；
- Normalized / semantic 结果或可重建索引；
- 用户设置；
- 关注球队；
- 通知调度状态（SC-017：已处理提醒的稳定键与结局，落在 settings 的 `notifications.firedReminders`，保留 30 天 / 最多 500 条）；
- Provider 数据版本；
- WebCal 缓存元数据。

原则：

- 原始数据与增强数据分离；
- schema migration 必须可控；
- 数据库损坏不应导致应用完全无法启动，应有恢复 / 重建策略。

## 12. 后台行为

避免高频轮询。

允许的后台触发：

- 应用启动；
- 用户手动刷新；
- WebCal 到达刷新时间；
- 下一条通知调度；
- 内置数据版本更新检查（低频）。

网络任务必须：

- 有超时；
- 可取消；
- 可失败重试；
- 不阻塞 UI；
- 暴露最近状态。

> 当前实现（SC-007）：WebCal 刷新由单一 `setTimeout` 驱动（应用启动、手动刷新、到达刷新时间三类触发），不使用轮询；网络任务带连接 / 总超时，失败后按 30 分钟重试，全程异步不阻塞 UI，来源状态（上次成功时间 / 错误 / 最近尝试时间）即最近状态。取消目前是“结果丢弃”：应用退出时停止调度器并放弃在途结果，尚未向 Rust 侧发送取消信号，HTTP 请求由 30s 总超时兜底。

> 当前实现（SC-017）：提醒调度也只用一个 `setTimeout`（没有轮询、没有 `setInterval`），它指向两者中更早的一个——下一条提醒，或下一个本地零点；触发后重新计算。跨天那一次除了唤醒还会按实时时钟重算计划（计划窗口是「当前日期起 30 天」，常驻数天的会话不能停留在启动那天的窗口），因此应用运行期间每个自然日最多多一次唤醒，关闭窗口后不会有任何额外唤醒。晚于容忍窗口（2 小时）的提醒记为已错过而不补发。调度器活在 webview 里，窗口隐藏时 Chromium 会节流后台定时器，提醒可能晚到不到一分钟；应用退出后仍能提醒的常驻调度不在 v0.1。

> 当前实现（SC-002）：窗口生命周期不新增任何后台唤醒源——Rust 侧没有定时器或轮询，窗口隐藏后只是不再渲染（Windows 实测：隐藏 30 秒内进程 CPU 时间增量 0s，可见空闲状态同样为 0s）。关闭窗口的语义由设置项 `app.closeBehavior` 决定（隐藏到托盘 / 退出），托盘、托盘菜单与单实例恢复窗口都走同一段“显示 → 取消最小化 → 聚焦”代码。只拦截关闭请求，最小化按钮保持系统默认。托盘不可用时“隐藏到托盘”退化为退出，并把实际生效的行为回报给界面，避免出现窗口藏起来却没有恢复入口的状态。

## 13. 错误与降级

### 网络失败

- 显示缓存；
- 标记刷新失败；
- 不删除旧数据。

### Matcher 失败

- 回退普通事件。

### Logo 缺失

- 使用文字缩写 / 通用图形；
- 不破坏布局。

### Provider 数据缺失

- 不伪造数据；
- 对未知值留空。

### 通知权限被禁用

- 在设置中显示状态；
- 日历本身继续可用。

> 当前实现（SC-017）：权限状态经 Rust 侧查询与请求（桌面端没有运行时授权对话框，恒为已允许，是否真正弹出由系统通知设置决定），侧栏「通知」组把它写成一句话——被拒绝时说明“提醒不会弹出，日历其他功能不受影响”并提供「请求系统授权」入口，没有桌面壳时说明“系统通知需要桌面环境”；发送失败按结构化原因（`permission-denied` / `send-failed`）映射成用户可读文案并显示在同一个位置，不假装送达。权限请求只在用户开启通知或显式点击时发生一次，不在后台反复询问。

> 当前实现（SC-019）：三条“不能落盘 / 读不出来”的原因分开说，界面不把它们混成一句失败。**没有桌面壳**（浏览器预览）与**桌面壳在但快照打不开**（磁盘错误、权限、迁移链缺失）是两件事：后者的状态行写「本地数据层不可用（<脱敏原因>）：日历可浏览，导入与订阅不可用，设置更改不会保存」，导入 / 订阅动作说明这次动作**不会发生**（不写成“发生了但没保存”），设置页顶部同样说明改动不写盘——故障不会被伪装成预览模式（`layout/data-layer-status.ts`，状态是一个联合类型，原因只在不可用时有意义）。**落盘失败**（数据层已打开但写不进去）由 App 的统一 `saveStore` 出口报告：「<动作>未能写入本地文件：<原因>（界面已按新状态显示，重启后可能丢失）」，任何一次成功写入即清除该提示，因此它陈述的是最近一次写入的结果而不是一段历史（`App.tsx`）。**快照里的坏记录**在读取边界逐条收窄（`data/store/schema.ts` 的 `narrowStoredEvent` / `narrowStoredSource`）：必需字段（uid / sourceId / title / start / allDay）不合格的事件整条隔离，可选字段类型不对只丢该字段，缺地址的订阅来源整条丢弃；被隔离的记录原文另存为 `<快照名>.rejected-<时间戳>`（与整份快照损坏时的 `.corrupt-` 同一口径，写失败不阻断启动），条数进状态行（「已跳过 N 个无法读取的事件」），主文件在下一次落盘时重新变干净。完整实现说明见 README「错误降级与可解释状态（SC-019）」。

## 14. 隐私与安全

v0.1 原则：

- 本地 ICS 不上传；
- WebCal 仅访问用户配置的 URL；
- 不默认遥测；
- 不建立云端账号依赖；
- 日历原始内容不发送给 AI 服务；
- 日志避免记录完整私密事件正文；
- URL 中的 token / secret 不应明文输出到普通日志。

未来若加入遥测，必须显式说明并允许关闭。

> 当前实现（SC-019）：脱敏原语只有一处（`reliability/redact.ts`）——地址保留协议（按原文，`webcal://` 不会被改写成 `https://`）/ 主机 / 路径、省略查询串与账号信息，`token=…` 这类没被识别成 URL 的裸凭据按白名单参数名抹掉值；事件正文（标题 / 标准化标题 / 描述 / 地点）替换为占位符；文案折叠空白并截断长度。**顺序是契约**：正文替换在折叠与截断之前做，否则超过上限的标题会留下没被替换的前缀。规则本身可测，但真正起作用的是一处结构性改动：Matcher / Resolver 的错误报告不再携带原始 `error` 对象，只带**在报告生成处就已洗过**的 `errorName` + `message`（引擎与解析链同时持有异常与事件，是唯一能做这件事的地方），因此日志侧拿不到未处理的正文，“某条实现把标题拼进 message”也不再等于把事件正文打进控制台。同类入口一并收口：IPC 失败文案、通知发送失败文案、落盘失败文案都过同一个原语，订阅地址在状态行与日志里只以脱敏形式出现。

## 15. 性能需求

v0.1 先建立基线，再根据实测锁定硬指标。

必须测量：

- 冷启动时间；
- 空闲内存；
- 空闲 CPU；
- 窗口隐藏时资源；
- 1,000 事件导入；
- 10,000 事件导入；
- 月切换耗时；
- Matcher 批处理耗时；
- WebCal 增量刷新；
- Logo / 图片缓存效果。

目标原则：

- 空闲状态接近无 CPU 活动；
- 不采用高频定时轮询；
- 月视图切换应感知即时；
- 大量事件不应阻塞 UI 线程。

> 当前实现（SC-002）：“窗口隐藏时资源”已实测——隐藏 30 秒内进程 CPU 时间增量 0s（可见空闲状态同样为 0s），Rust 侧没有计时器，隐藏只是停止渲染；窗口最小尺寸（820×560）落在左右栏自动折叠阈值之内，最窄时月历主体仍完整。冷启动时间、空闲内存 / CPU 与导入耗时的完整基线仍由 SC-020 建立。

> 当前实现（SC-020）：基线已建立，方法与数字写入 [performance.md](performance.md)（可重复的 `npm run bench` + `tools/measure-desktop.ps1`、固定且确定性的工作负载、实测表格、缓存失效清单）。要点：冷启动中位 282 ms；空闲内存 26 MB 工作集 / 5 MB 私有；可见空闲与隐藏窗口的 30 秒 CPU 增量 0.000–0.031 s（隐藏后主窗口确认不可见）；10,000 条事件的月切换展开 152 ms（1,000 条 16.2 ms；优化前同机 597 ms）；10,000 条导入的解析 + 落库 83 ms、应用侧一次导入总时长 320 ms；Matcher 批处理 57.7 ms；WebCal 304 命中缓存无可测量的解析开销（200 全量替换 86.6 ms）。「大量事件不阻塞 UI 线程」按可安全分片的两段落实：语义增强改为分片执行（每 500 条一片，片间用 MessageChannel 任务让出主线程，单片约 3 ms），启动重建、订阅刷新与导入三条路径都走它；月视图读取也改为分片（按让出阈值每 5 ms 检查一次，10,000 条下单次任务 6.6 ms、最坏一次约 14 ms，改动前是一次约 164 ms 的同步计算），第一个任务在渲染期跑，约 200 条以下首帧即完整月格，更大的日历进入整理状态并给出可解释状态行；提醒计划的重建同样分片（展开 30 天窗口的 154 ms 拆成短任务，调度器的同步 `plan` 回调读一份「最近一次算完的计划」，未就绪前计划为空）；304 / 失败的刷新不再重读事件（存储的 `eventsRevision()` 只在事件集合真的变过时推进）；分片带来的重叠风险（两次重建交错会让增强分区混进旧快照的产物）由「同一次存储上的重建排队」消除。剩余的不中断同步段（导入解析 / 落库、月切换里剩余的毫秒级段）在 performance.md §6 如实记录为已知边界。§15 要求的「Logo / 图片缓存效果」在 v0.1 无对应物：仓库不分发图片，解析无状态，接入资源包后由 WebView 自己的图片缓存负责。本文件不写死性能门槛——按「先建立基线，再根据实测锁定硬指标」，硬指标在发布前从这份基线取数。

## 21. 需求变更规则

任何新增需求先判断：

1. 是否影响“日历本身可靠”；
2. 是否属于 v0.1；

5. 是否破坏本地优先；
6. 是否已有更简单的确定性方案。

如果需求会扩大范围，但不帮助完成 v0.1 垂直切片，应默认延期到后续版本。
