# 开发原则与建议做法

本文用于约束项目在早期开发阶段的方向，避免功能快速增加后失去结构。

## 1. 先做可运行的垂直切片

不要一开始就把所有 Provider、Matcher 和数据层全部设计完。

更推荐先完成一条完整链路：

```text
导入一个 ICS
→ 显示在月视图
→ 识别一场英超比赛
→ 显示球队徽标
→ 触发本地提醒
```

一条真实可运行链路，通常比大量抽象接口更能暴露真正的架构问题。

---

## 2. 不为未来过度设计

第一版只为已经明确的需求留扩展点。

例如 Matcher 应该可扩展，但暂时不需要：

- 在线插件市场
- 动态加载第三方二进制插件
- 复杂权限沙箱
- 跨进程插件 RPC

先使用简单、可测试的静态注册机制。

---

## 3. 业务规则不进入 UI

任何“根据事件内容判断类型”的代码，都应尽量放在 Matcher。

UI 只负责：

- 排版
- 交互
- 状态展示
- 用户设置
- 调用统一接口

这样以后替换 UI 框架或做移动端时，核心逻辑仍可复用。

---

## 4. 保留原始数据

语义增强不应该破坏原事件。

建议始终保存：

- 原始标题
- 原始描述
- 原始时间
- 原始 UID
- 原始来源

增强数据作为额外字段存在。

这样如果 Matcher 识别错误，可以重新识别，而不需要重新下载原始日历。

---

## 5. 识别结果要允许“不确定”

不要强迫所有 Matcher 给出确定答案。

建议 MatchResult 支持置信度或匹配原因。

例如：

```ts
type MatchResult = {
  semantic: SemanticEvent
  confidence: number
  reason?: string
}
```

对于模糊事件，可以选择不增强，而不是错误增强。

---

## 6. 确定性规则优先

像以下领域：

- 二十四节气
- 法定节假日
- 英超球队
- 明确格式的比赛标题

优先使用规则、词典和结构化数据。

这会带来：

- 更低资源占用
- 更容易测试
- 更稳定
- 更隐私
- 更容易离线工作

AI 或模型能力可以留给未来真正模糊的文本分类，而不应该成为基础依赖。

---

## 7. 性能预算从第一版开始记录

建议从第一个可运行版本开始记录：

- 冷启动时间
- 空闲内存
- 空闲 CPU
- 导入 1,000 / 10,000 个事件的耗时
- 月视图切换耗时
- Matcher 批处理耗时

早期先建立基线，不必立刻设非常激进的数字目标。

---

## 8. 后台任务尽量事件驱动

避免高频轮询。

优先使用：

- 系统定时器
- 订阅刷新间隔
- 文件变更事件
- 应用启动时刷新
- 明确的下一次提醒时间

常驻应用真正容易浪费资源的地方，往往不是 UI，而是后台唤醒。

---

## 9. 网络功能必须可解释

用户应该知道：

- 哪些日历是本地的
- 哪些来自网络
- 上次更新时间
- 下次刷新时间
- 刷新失败原因

不要在后台产生无法解释的网络请求。

---

## 10. 第三方 Logo 与数据版权要单独处理

球队徽标、联赛 Logo 和部分体育数据可能有商标或授权问题。

建议：

- 代码和元数据与 Logo 资源分离；
- 在正式发布前确认资源许可；
- 必要时只提供用户自行配置的资源路径；
- 不因为开发方便就默认把来源不明的图片提交到仓库。

---

## 11. 测试优先覆盖核心规则

最值得测试的不是视觉细节，而是：

- ICS 解析
- 时区
- 重复事件
- Matcher
- 节假日日期
- 二十四节气
- 提醒时间计算

尤其是时间和时区代码，需要尽早建立测试样例。

---

## 12. 提交保持小而明确

建议提交信息保持统一：

```text
feat: 添加 ICS 导入
fix: 修复跨时区全天事件
docs: 补充 Matcher 设计
refactor: 拆分事件标准化逻辑
test: 添加英超标题识别测试
```

每个提交尽量只解决一个问题，方便回滚、Review 和定位回归。

---

## 13. 文档只记录真实方向

设计文档允许变化。

如果实现与文档不一致，应该及时更新文档，而不是保留一套“理想架构”和另一套“真实代码”。

本项目优先追求可理解、可维护和可验证。
